# KCK1001: Commit through IUnitOfWork so domain events are dispatched

> Available from 4.7.0, in the `Kck.Persistence.EntityFramework` package (ADR-0031).

| | |
|---|---|
| Severity | Warning |
| Category | `Kck.Persistence` |
| Code fix | No (see below) |

## Cause

A transaction is committed directly with `IDbContextTransaction.Commit` or `CommitAsync`, in a project that uses domain
events: it implements `IDomainEventHandler<T>` or `IDomainEventDispatcher`, or calls `AddDomainEventHandlers` /
`AddDomainEventDispatch`. Projects without domain events get no warning.

The rule needs the whole project, so it is reported when the project builds, not while you type. It sees one project
at a time: a data-access project that commits directly while the handlers and their registration live only in other
projects is not reported.

## Why it matters

Domain events saved inside a transaction wait for that transaction. `IUnitOfWork.CommitAsync` dispatches them right
after the commit. A transaction committed directly leaves them waiting for the context's next `SaveChanges`; if none
follows, they are lost without a trace (see [Interceptors](../../providers/persistence.md#interceptors)).

```csharp
using Microsoft.EntityFrameworkCore;

public sealed class PlaceOrderService(AppDbContext db)
{
    public async Task PlaceAsync(Order order, CancellationToken ct)
    {
        await using var transaction = await db.Database.BeginTransactionAsync(ct);
        db.Orders.Add(order);
        await db.SaveChangesAsync(ct);   // events raised here wait for the commit
        await transaction.CommitAsync(ct); // KCK1001: nothing dispatches them now
    }
}
```

## How to fix

Open, commit and roll back the transaction through `IUnitOfWork`:

```csharp
using Kck.Persistence.Abstractions.UnitOfWork;

public sealed class PlaceOrderService(IUnitOfWork unitOfWork)
{
    public async Task PlaceAsync(Order order, CancellationToken ct)
    {
        await unitOfWork.BeginTransactionAsync(ct);
        await unitOfWork.Repository<Order, Guid>().AddAsync(order, ct);
        await unitOfWork.SaveChangesAsync(cancellationToken: ct);
        await unitOfWork.CommitAsync(ct); // events are dispatched after the commit
    }
}
```

Make the change by hand, and check three things it can change (which is why there is no automatic fix):

- **Early exits.** `await using var transaction = ...` rolled back on every `return`, `continue` or exception. With
  `IUnitOfWork`, call `RollbackAsync` on those paths yourself, or the next `CommitAsync` commits the rows too.
- **Rollback in `catch`.** `IUnitOfWork.CommitAsync` releases the transaction whether the commit succeeds or fails,
  so do not call `RollbackAsync` after it: that throws "No active transaction" and hides the original error.
- **Which context.** `IUnitOfWork` uses the scope's registered `DbContext`. A transaction on a context created by a
  factory or on another context type is a different transaction; keep it as it is and suppress the warning.

## When to suppress

If the direct commit is intended (for example a transaction that saves no entity with domain events), suppress the
warning where it occurs:

```csharp
#pragma warning disable KCK1001 // no domain events in this transaction
```

or for a whole project in `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.KCK1001.severity = none
```
